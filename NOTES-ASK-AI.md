# Asking the AI about your study notes

Generated notes are LLM output. They can be wrong, and until this change a student
reading them had **no way to challenge a line** — the tutor was not reachable at
all from Notes Focus Mode, and nothing anywhere in the app let you point at a
sentence and ask about it.

Three affordances now do:

| Where | What |
|---|---|
| **Select any text** in the notebook | popover with **💡 Explain · ✅ Verify · 📝 Example · 💬 Ask…** |
| **💬 on each section heading** | same four actions for the whole section (heading + everything under it) |
| **🔍 Check notes** in the Focus toolbar | one pass over the entire note, claim by claim, against the lecture |

All three work in Notes Focus Mode **and** in the ordinary AI Study panel, because
Focus Mode moves the original note DOM rather than cloning it.

## Why the tutor needed a third "dock"

Focus Mode promotes `#ai-sub` to a fixed layer at `z-index: 2147483000` and marks
every element outside it `inert`. The global floating tutor is therefore painted
*underneath* the notes and unclickable — `tutor-float.js` hides it outright while
Focus is up.

There is also a trap: `sendTutor()` only paints a reply when `tutorVisible()` is
true. Simply un-hiding the float would have produced an answer that streamed,
saved to localStorage, and **never appeared**.

So the chat gets a third dock alongside `panel` and `float`: **`focus`**, an ask
sheet inside the notes subtree (`#ai-focus-ask`). The single `.ai-tutor-shell`
node is *re-parented* into it exactly as it is into the floating window, so a
reply that is mid-stream when the sheet opens or closes keeps painting. The sheet
is laid out as the last flex child rather than as an overlay, so the notes stay
readable while you ask about them.

## Grounding: `note_excerpt`

The passage travels in its own request field, not glued into the question:

```json
{ "id": "...", "q": "Verify this line from my notes: \"…\"",
  "note_excerpt": "<the full passage>", "note_ts": 754 }
```

Sending it separately keeps the chat bubble readable, keeps the passage out of the
2000-char history truncation, and stops the memory profiler learning a wall of
quoted notes as though the student had said it.

**The important part is how the server frames it** (`_NOTE_PASSAGE_RULE` in
`youtube-turbo-proxy/app.py`): the passage is the *subject* of the question, never
evidence. The notes were generated by an AI from the same transcript, so treating
them as a source would let the model confirm its own earlier mistake back to the
student — the exact failure "verify this" exists to catch. The rules say:

- the **transcript outranks the passage**; if they disagree, say so and correct it
- open with a verdict — ✅ matches the lecture / ⚠ not covered here / ❌ contradicts
- absent from the lecture does **not** mean false — say it is not in this lecture,
  then say whether it is actually correct

`note_ts` comes from the "Follow the lecture" index, so a passage is tied to a real
moment in the video. Blocks without their own `[mm:ss]` marker inherit the nearest
preceding one. The server uses it twice: it tells the model where to look, and
when a lecture is longer than the model's context budget it **centres the
transcript window on that moment** instead of taking a head slice (`_transcript_window`).
Without that, a question about the last section of a long lecture was answered
from a transcript that had been truncated before it.

## Verify forces a live web lookup

`✅ Verify` sends `web: 'on'` regardless of the 🌐 setting. Checking whether a fact
is still true against stale training data is the failure being fixed, not a cheaper
version of it. The whole-note **🔍 Check** deliberately does *not* search: its
question is a formatting instruction with no searchable subject, and the transcript
is the right authority for "does my note match the lecture".

## Free-tier allowance

The free plan allows 5 tutor messages/day. One tap per section makes that easy to
burn through by accident, and discovering it by hitting the wall reads as the
feature being broken. The ask sheet header therefore shows `N of 5 free left today`.

**The server owns that number.** It is returned as `quota: {left, max}` on every
tutor answer *and* on the `rate_limited` refusal, computed by `_rate_left()` — a
non-consuming read of the same rolling window `_rate_ok()` meters.

That matters because the browser cannot work it out. The backend counts a rolling
24 hours per **account**; the local gate counts messages sent from **this device**
inside one calendar day. `toISOString()` rolls over at 00:00 UTC = 05:30 IST, so a
student who spent five messages at 11pm used to see a fresh allowance at dawn while
the server was still refusing — the UI promised five and the server delivered a
429. The local counter is now only an estimate used before the first answer of a
session, it is keyed to the **IST** day so it does not reset mid-study-night, and
`window.ezTutorMarkExhausted()` pushes a server refusal back into it so the gate,
the counter and the server agree.

`window.ezTutorMessagesLeft()` still lives in
`js/features/preppath-phase4-gating.js` because that file owns the key format and
the limit. It counts nothing, and returns `null` for Pro/trial.

## Details worth knowing before changing this

- **Two hosts get a 💬 button: `.sec` headings and MCQ `.q-head` bars.** Both are
  already flex rows, so a child pushed over with `margin-left:auto` cannot make the
  block taller. The private annotation canvas is absolutely positioned over the
  notebook and its saved strokes are anchored to that geometry, so a change in
  block height here would visibly shift every existing highlight.
- **MCQ cards matter more than headings, not less.** `nbMCQ()` emits `.qkeep` per
  question and only calls `nbInner()` for prose between them, so MCQ-style notes
  originally had no ask button anywhere — and a hallucinated answer key is the
  single most damaging thing generated notes can contain. An MCQ passage also has
  to reach forward to its `.explain` block, which `nbCard()` emits as a *sibling*
  of `.qkeep` rather than a child.
- **Selection is disarmed while drawing.** The annotation canvas takes pointer
  events for every tool except `move`, so the popover and the buttons are dimmed
  and disabled then (`.ai-focus-marking`).
- **`pointerup`, not `selectionchange`.** `selectionchange` fires continuously
  through a drag and sends the popover skating across the screen.
- **Esc unwinds innermost-first**: popover → ask sheet → annotation bar → Focus
  Mode. Otherwise Esc would tear down the whole reading view mid-question.
- **A staged passage ("Ask…") attaches to exactly one message**, then clears, and
  expires after 5 minutes so it can never attach to an unrelated later question.
- **Note actions force Video scope.** The library endpoint ignores `note_excerpt`,
  so a note question asked in Library scope would silently lose its passage.
- **`noteBlockText` strips** the injected button, the decorative `.num` counter
  (which would otherwise read "1Fundamental Rights") and the `⏩` glyph that
  `linkTs()` prefixes timestamps with.

- **The section button and the selection handler share one element**, so the
  selection handlers explicitly ignore events from `.ai-nb-ask` and `#ai-note-pop`
  (`fromNoteAffordance`). Without that guard the desktop event order —
  `pointerdown`, `pointerup`, `click` — meant the click opened the popover and the
  `pointerup`'s deferred `settle()` closed it ~10 ms later, because a button click
  selects no text. It reproduced on desktop only: touch delays `click` past the
  timer. Covered by a sequenced regression test.
- **A second tap on the same section button dismisses the popover.** It is
  anchored by block index, so tapping a *different* section re-anchors instead.


## Inverted (night) reading — the ◐ toggle

The notebook is a deliberately light "paper" surface, which is punishing in a dark
room. `◐` in the Focus toolbar flips it to dark paper / light ink, and the choice
is remembered (`aiNotesInvert`).

It sits in the **heading cluster** next to Exit and Full screen, not in the actions
row on the right — that row scrolls sideways on a phone, and a display toggle
should not be able to slide off screen.

### Why a filter and not a dark palette

`nbCss()` carries ~55 rules of hard-coded light colour: headings in five accents,
fact/mem/note boxes, MCQ cards, tables, chips, badges. A parallel dark copy would
drift out of sync with the light one the first time either side was touched. One
declaration does the whole thing instead:

```css
filter: invert(1) hue-rotate(180deg);
```

The `hue-rotate` is what makes it usable rather than psychedelic — it puts hues
roughly back where they started, so green headings stay green instead of turning
magenta.

### Why it is on the scroller, not the layer

The filter is applied to `> .ai-scroll`, never to `#ai-sub` itself:

- The toolbar, annotation bar, ask sheet, selection popover and mini video are all
  **siblings** of the scroller. They are darkened explicitly instead of being
  double-inverted — and the video keeps true colour.
- **`filter` makes an element a containing block for `position: fixed`
  descendants.** `#ai-note-pop` is fixed; putting a filter on its ancestor would
  break its positioning outright.
- The annotation canvas *is* inside the scroller, so it is counter-inverted — a red
  pen stays red, because the student picked that colour.
- The **PDF export** renders from the `nbHtml` string with its own print CSS, so it
  is untouched and never prints white-on-black.

The UA fullscreen rules restate the light paper with `!important`, so the inverted
variants restate it too (`:fullscreen`, `:-webkit-full-screen`, `::backdrop`) —
otherwise going full screen snapped the background back to paper.

**Trade-off:** a filtered scroller is a composited layer, so very long notes may
cost some scroll smoothness on low-end phones. If that shows up in practice, the
fallback is a real dark palette for the handful of `nbCss` rules that carry most of
the surface area.
